# Goal
Transition `tori-agent` from loose, text-based artifact management to a strictly typed, schema-driven ontological system. This upgrade ensures structural integrity across all managed artifacts, enables capability-based agent dispatching, and introduces relational dependency tracking in developer tools.

# Scope
### In scope
- **Tier 1 (Contract):** Pure JSON Schema in `packages/ontology/` — zero dependencies, the source of truth for all 12 core ontology classes.
- **Tier 2 (Types):** Build-time TypeScript interfaces generated from Tier 1 via `json-schema-to-typescript`.
- **Tier 3 (Validation):** Runtime Zod validation only in `packages/core/src/tools/lifecycle.ts` (the harness).
- **Neuro-symbolic Triad:** JSON-LD/OWL (meaning/inference) → SHACL (validation/shapes) → Datalog/Soufflé (policy/operational reasoning).
- **Capability Dispatch:** In-memory reverse index `Map<Capability, AgentID[]>` for O(1) lookup, built from `capabilities.json` manifest generated by `cli generate`.
- **Tiered Validation:** Shallow validation during execution, deep (SHACL + Datalog) only at verify stage.
- **Schema Distillation:** Never inject raw JSON schemas into LLM prompts; use TypeScript-lite interfaces or few-shot examples.
- **Discovery:** JIT incremental indexing via file-watcher (chokidar), not full build-time scan.
- **Error Reporting:** Source-mapped validation errors with file path and line numbers.
- **CLI:** `tori inspect <agent_id>` command to expose distilled prompt/schema for debugging; `tori ontology` subcommands for validate, diff, migrate, status.

### Out of scope
- Changing the underlying storage format (still files on disk).
- Refactoring the `runtime` packages (they should consume the new schemas, not define them).
- Implementing a centralized database for the registry (it remains distributed in agent specs).
- Full OWL reasoning engine (inference is limited to Datalog rules).
- External triple store / SPARQL endpoint.
- Real-time graph synchronization across distributed agents.

# Open questions
- **Schema Format:** RESOLVED — Three-Tier Architecture adopted. Tier 1: Pure JSON Schema in `packages/ontology/`. Tier 2: Build-time TS interfaces via `json-schema-to-typescript`. Tier 3: Runtime Zod only in harness.
- **Registry Discovery:** RESOLVED — Manifest-based discovery. `cli generate` writes `capabilities.json`. In-memory `Map<Capability, AgentID[]>` reverse index. JIT re-indexing via chokidar.
- **Relational Syntax:** RESOLVED — Fuzzy Markdown references. Humans write prose (`depends on`, `requires`, `blocks`); scribe agents formalize into JSON-LD during verify phase.
