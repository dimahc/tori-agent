## Goal

Make the review cluster's hand-off contract structurally leaner (not lexically compressed) so multi-round reviews don't linearly balloon team-lead's context, give the cluster an architecture/design-quality lens it currently has zero coverage for, and finish wiring the already-specced mechanical pre-filter into `review-manager` so trivial lint/test failures never cost a semantic reviewer call. Also replace `prompt.md`'s soft context-management language with a mechanical, checkable rule.

## Scope

### In scope
- One shared, single-source-of-truth doc for structural report compression rules, referenced (not duplicated) by the 4 review-cluster prompts.
- A new `architecture-reviewer` agent, wired through `index.js` exactly like the existing reviewers, spawned conditionally by `review-manager` when a change introduces a new module/service boundary.
- Wiring `docs/specs/review-manager-mechanical-checks.md`'s already-designed lint/test short-circuit into the live `agents/review-manager.md` prompt, and reconciling that spec's frontmatter/body status mismatch.
- Converting `agents/prompt.md`'s Context Management triggers to a concrete, mechanical rule.
- CHANGELOG entries for all of the above (user-facing framing only).

### Out of scope
- `docs/briefs/plugin-v2-migration.md` — do not touch or reference.
- `team-lead-workflow/` (the React SPA docs site) — no changes.
- The separate VitePress `website/` portal (`website/*.md`) — this plan updates the canonical `docs/specs/*.md` sources; mirroring those changes into `website/` is a documentation-sync concern for `gardener`, not this plan.
- Any new agent unrelated to the two axes (compression contract, architecture lens).
- Any change to the default-deny permission philosophy — new capabilities are still explicit per-agent allowlists in `index.js`, following existing patterns (e.g. `gardener`'s scoped `bash` allowlist).
- Any token-counting/budget tool or numeric token-reduction target — success is qualitative/structural (before/after report-shape inspection).
- `agents/brainstorm.md` — untouched.
- `bug-finder`/`explore` output compression — the brief flags this as worth *evaluating*, not implementing. Not part of this plan; if wanted, it's a separate follow-up mission.

## Building blocks

- [x] Block 1: Shared compression-contract doc + reviewer prompt pointers
  - **What**: Create `docs/specs/review-report-contract.md` (new file, using the `spec-writer` skill / `docs/templates/agent-doc.md` conventions: frontmatter with `status`, `created`; card/table format, no argumentative prose). It documents, once:
    - The structural compression rules: cap/strip narrative sections, collapse a clean "no issues" verdict to a single acknowledgment line (not a paragraph), and a concrete issue-ID scheme (e.g. sequential `#N` per review round, assigned by `review-manager`) so a later round can say "issue #2 fixed" instead of re-printing the original finding.
    - An explicit non-goal callout: this is NOT lexical/caveman compression — fields that arbitration depends on (security-reviewer's `Attack vector:`, requirements-reviewer's evidence table row) must stay fully intact, grammar and all.
    - **Why this location over `docs/guiding-principles.md`**: `guiding-principles.md` holds repo-wide human/CI-enforced engineering norms (git hygiene, zero-deps, CHANGELOG conventions). This contract is a review-cluster-specific behavioral protocol, same category as `review-cluster.md` and `review-manager-mechanical-checks.md` — it belongs next to them in `docs/specs/`, not mixed into the general principles file.
  - **Edits to the 4 existing prompts** (`agents/code-reviewer.md`, `agents/security-reviewer.md`, `agents/requirements-reviewer.md`, `agents/review-manager.md`): each gets a short new subsection (2-5 lines, not a restatement of the full contract) that (a) points to `docs/specs/review-report-contract.md` for the full rationale, and (b) states the one or two actionable rules the agent must actually follow inline (so it doesn't need to `read` the doc every review just to behave correctly — the doc is the source of truth for humans maintaining the rule, not a runtime dependency). Concretely:
    - `code-reviewer.md`, `security-reviewer.md`, `requirements-reviewer.md`: their `Output Format` template's "Positive Notes" section must become conditionally single-line when there are no issues (today it's an unconditional free-text block). `security-reviewer.md`'s existing Auth/Token/Crypto Acknowledgment Rule already produces a one-liner — keep it, just add the pointer.
    - `review-manager.md`: gets the cross-round referencing rule — when synthesizing round 2+, previously-resolved findings are referenced by their prior `#N` ID ("issue #2 — fixed"), not re-described. Update its `Output Format` block (`### Issues` section) to show this convention.
  - **Done when**: `docs/specs/review-report-contract.md` exists and is linked from `docs/specs/review-cluster.md`'s `## Liens` section; each of the 4 prompt files contains a pointer subsection referencing it (grep for `review-report-contract.md` returns exactly 4 hits across `agents/*.md`, plus its own file); the full compression ruleset text does NOT appear duplicated verbatim across the 4 prompts (only the doc has the full version); the "no issues" case in each prompt's Output Format is explicitly single-line, verifiable by reading the template.

## Decision log

- **Compression-contract location: `docs/specs/review-report-contract.md`, not `docs/guiding-principles.md`.** Decided during planning. Rationale: `guiding-principles.md` is repo-wide human/CI-enforced engineering norms; this contract is a review-cluster-specific agent behavior protocol, the same category as the two existing files it sits beside in `docs/specs/`.
- **OQ1 resolved — Option (b): new `runMechanicalChecks` lifecycle tool, `review-manager` stays bash-free.** Implemented `tools/lifecycle.js`'s `runMechanicalChecks(projectRoot)` (6th deterministic lifecycle tool, using `node:child_process`'s `spawnSync`), registered as the `run_mechanical_checks` plugin tool in `index.js`, and granted only to `review-manager`'s permission block (no `bash`). Rationale: fits the existing "N deterministic lifecycle tools" pattern, keeps `review-manager`'s permission surface unchanged (still no shell access), and produces a structured, testable result instead of raw prompt-driven shell invocations.
- **OQ2 resolved — `distill`/`prune` confirmed non-existent, brief's premise was stale.** Re-verified during Block 4 implementation: `index.js`'s `team-lead` permission block lists only `compress` (no `distill`, no `prune`), and grepping `agents/prompt.md` for `distill`/`prune` returns zero matches — the tools were already fully removed from the prompt in a prior change (see `CHANGELOG.md` `[Unreleased]` → Changed: "distill and prune were removed since they don't exist in OpenCode's toolset"). No permissions were re-added and no usage instructions were written for either tool. Block 4's only actionable work was therefore the mechanical compress-trigger rewrite; the distill/prune sub-part required no file changes, only this confirmation.
- **OQ3 resolved — `architecture-reviewer` is additive, outside the "max 3 technical reviewers" cap, same treatment as `requirements-reviewer` (mandatory-when-triggered).** Rationale: the cap exists to prevent reviewer pile-up on ordinary changes. `architecture-reviewer` only spawns on structural changes (new module/service boundary), which are rare by construction — making it additive doesn't undermine the cap's purpose because it won't stack with the size-based proportionality logic on typical reviews. Implemented in `agents/review-manager.md`'s Proportionality rules and Cap row, and reflected in `docs/specs/review-cluster.md`'s reviewer-selection description.
